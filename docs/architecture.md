## 1. ข้อมูลเดินทางยังไงตั้งแต่ต้นจนถึงหน้าจอ

### ภาพรวม — 2 สายที่แยกกันสนิท เจอกันแค่ที่ฐานข้อมูล

```
สายที่ 1  เติมข้อมูล (ไม่มีผู้ใช้เกี่ยวข้อง)
  cron-job.org → POST /internal/cron?step= → getData → mapping → saveData
                                                                     │
                                                                     ▼
                                                              PostgreSQL
                                                                     │
สายที่ 2  แสดงผล (ผู้ใช้เปิดแอป)                                       ▼
  Flutter → dio → GET /matchcoming → FastAPI อ่าน DB → fromjson → provider → จอ
```

**cron ไม่เคยแสดงอะไร · Flutter ไม่เคยคุยกับ PandaScore** ทั้งคู่รู้จักแค่ฐานข้อมูลตรงกลาง

ผลที่ได้

- ผู้ใช้เปิดแอปแล้วเห็นข้อมูลใน 2 วินาที ไม่ต้องรอสายพานทั้งเส้น (`match` ใช้เวลา 131 วินาที)
- PandaScore ล่ม แอปยังใช้ได้ปกติ แค่ข้อมูลไม่สดเท่านั้น

---

### สายที่ 1 — เติมข้อมูล

ข้อมูลภายนอก เช่น match / team / tournament ดึงมาจาก external API
ชนิดข้อมูลที่ได้มาส่วนใหญ่เป็น JSON ส่วน backend เป็น FastAPI

| | อยู่ไฟล์ไหน | หน้าที่ |
|---|---|---|
| **model** | `models/` | ตารางในฐานข้อมูลหน้าตายังไง |
| **schema** | `schemas/` | API ของเรารับ/ส่งอะไร |
| **mapper** | `services/*/map.py` | คัดว่าจะเก็บ field ไหนจาก JSON ที่ได้มา |

#### ใครเป็นคนสั่งให้ไปดึง

backend เป็น web server — **นั่งรออย่างเดียว ไม่มีนาฬิกาของตัวเอง** ไม่มีใครยิงเข้ามาก็ไม่ทำอะไรเลย

หลัง deploy จึงต้องมีคนข้างนอกมาปลุก ใช้ **cron-job.org** ยิง `POST /internal/cron?step=` เข้ามาตามรอบเวลา

> ไม่ใช่ real-time แต่เป็น **อัปเดตตามรอบเวลา** — ข้อมูลเปลี่ยนแล้วรู้ภายใน 30 นาที

#### cron 5 ตัว

**มี endpoint เดียว เปลี่ยนแค่ `?step=`** ไม่ได้ทำ endpoint แยกตัวละงาน

| # | ยิงอะไร | ทุกเท่าไหร่ | ทำอะไร |
|---|---|---|---|
| 1 | `GET /health` | 5 นาที | ปลุกไม่ให้ Render หลับ เพราะใช้แพ็กฟรี **ถ้าไม่มีตัวนี้อีก 4 ตัวพังหมด** |
| 2 | `?step=match` | 30 นาที | sync แมตช์ |
| 3 | `?step=all` | วันละครั้ง | ทุกขั้น + ตาข่ายนิรภัย |
| 4 | `?step=patch,summary,analysis` | 6 ชั่วโมง | แพตช์ใหม่ + งาน AI |
| 5 | `?step=notify` | 10 นาที | ส่งแจ้งเตือน |

**ตัวที่ 2 — เส้นทางเต็ม ๆ**

```
POST /internal/cron?step=match
  → syncMatch()
  → getPandaMatch()   ยิง request ไป PandaScore ต้องแนบ header ไปด้วย
  → ได้ JSON กลับมา
  → mapping ด้วย raw เข้าถึงทีละ field
  → saveMatch()       บันทึกลง PostgreSQL (Supabase)
```

**ตัวที่ 3 — `all` ซ้ำกับตัวอื่นเกือบหมด แล้วมีไว้ทำไม**

```
all = tour + match + patch + summary + analysis
      ^^^^   └───┘   └────────┬─────────┘
       │    ตัว 2 ทำ         ตัว 4 ทำ
       └── ตัวเดียวที่ไม่มี cron อื่นทำให้  ทัวร์นาเมนต์ใหม่จึงเข้าระบบวันละครั้ง
```

และเป็น **ตาข่ายนิรภัย** อีกชั้น เผื่อตัว 2 หรือ 4 พลาดไปทั้งวันโดยไม่มีใครสังเกต

**ตัวที่ 4** — แยกออกจากตัวที่ 2 เพราะขั้น AI กินโควต้า Gemini ยิงถี่ทุก 30 นาทีไม่คุ้มและไม่จำเป็น แพตช์ออกราวสองสัปดาห์ครั้ง

**ตัวที่ 5** — ต้องถี่ 10 นาที เพราะต้องเตือนก่อนแมตช์เริ่ม 15 นาที ถ้ายิงทุก 30 นาทีจะพลาดหน้าต่างเวลานั้นไปเลย

#### ขั้น AI — เติมทีหลัง ไม่ได้มาพร้อมข้อมูลดิบ

สายที่ 1 มี 2 ช่วง ไม่ใช่ช่วงเดียว

```
ช่วง A  เติมข้อมูลดิบ      cron #2
  PandaScore → map → save
  match_analysis ถูกสร้างเป็นแถวเปล่า  status = pending

ช่วง B  เติมความคิดเห็น    cron #4
  อ่านแถวที่ pending → ส่งเข้า Gemini → เขียนกลับลงแถวเดิม  status = ready
```

`win_pct_a` · `reasoning_th` · `ai_summary_th` **PandaScore ไม่เคยส่งอะไรแบบนี้มาเลย** Gemini เป็นคนเขียน

**ทำไมต้องแยก 2 ช่วง**

```
รวมกัน   sync แมตช์ทีไรต้องเรียก Gemini ทุกแถว       โควต้าหมดใน 2 วัน
แยกกัน   ช่วง B กรอง status != ready                เรียกเฉพาะของใหม่
```

### สายที่ 2 — แสดงผล

```
Flutter → dio → GET /matchcoming → FastAPI → PostgreSQL
                                   ^^^^^^^   ^^^^^^^^^^
                                คนเดียวที่คุยกับ DB
```

**Flutter ไม่เคยแตะฐานข้อมูลเลย** ถ้าต่อตรงได้ก็ไม่ต้องมี backend และ connection string จะต้องฝังอยู่ในแอป ใครแกะ apk ก็เอาไปได้

#### ฝั่ง Flutter ไม่ได้จบที่ dio

```
dio                        ได้ Map<String, dynamic>   ยังเป็น JSON ดิบ
dataModel.fromjson(json)   แปลงเป็น object ของ Dart
provider                   เก็บผลที่แปลงแล้ว ใครขออีกก็ได้ของเดิม ไม่ยิงซ้ำ
ref.watch                  widget สมัครฟัง ค่าเปลี่ยน → วาดใหม่
Widget                     m.teamA.teamName ขึ้นจอ
```

`fromjson` คือคู่ตรงข้ามของ `map.py` ฝั่ง backend — **สายพานมีตัวแปลงอยู่หัวท้าย**

#### Riverpod — เลือก provider จากอะไร

| ชนิด | ใช้เมื่อ | ตัวอย่าง |
|---|---|---|
| `FutureProvider` | รับข้อมูลมาแสดงอย่างเดียว | match · patch · tour · bracket |
| `AsyncNotifierProvider` | อ่าน + เขียนกลับไปที่ server | follow · noti · profile |
| `NotifierProvider` | เก็บค่าในเครื่อง ไม่ต้องรอ | theme · locale · noti switch |

#### widget ที่อ่าน provider ได้

`ref` ไม่ได้ลอยมาเอง ต้องมี widget ที่ให้มันมา

| ชนิด | ใช้เมื่อ |
|---|---|
| `ConsumerWidget` | ไม่มี state ของตัวเอง แค่อ่าน provider |
| `ConsumerStatefulWidget` | มี `setState` หรือ `initState` ของตัวเองด้วย เช่น `_busy` ใน `AccountTile` |

```
ref.watch   ใน build        สมัครฟัง ค่าเปลี่ยน → วาดใหม่
ref.read    ใน callback     อ่านครั้งเดียว ไม่สนใจว่าจะเปลี่ยนทีหลังไหม
```

ใช้สลับกันเมื่อไหร่จะได้บั๊กเงียบ — `read` ใน `build` แล้วจอไม่อัปเดต

## 2. ทำไมต้องมี `sync_run.py` แยกจาก `sync.py` และ `cron.py`

### ปัญหา

ตอนแรกโค้ด sync อยู่ใน `sync.py` ทั้งหมด ซึ่ง **อ่าน `argv` และ `print`**

พอต้องให้ cron ยิงเข้ามาทาง HTTP ก็ใช้ของเดิมไม่ได้

```
HTTP ไม่มี argv
และไม่มีใครนั่งดู terminal ของ Render
```

### ถ้าไม่แยก แล้วรวมไว้ที่เดียวล่ะ

```python
# api/cron.py
from sync import main
main(["sync.py", "match"])   # ต้องปลอมอาร์กิวเมนต์บรรทัดคำสั่งขึ้นมา
                             # แล้วผลที่ได้คือ exit code กับ print
                             # HTTP เอาไปใช้ไม่ได้เลย
```

ใช้ไม่ได้ ก็ต้องไม่เรียก `main` แต่ไปเรียกฟังก์ชันข้างในแทน — **พอทำแบบนั้น ฟังก์ชันข้างในนั่นแหละคือ "ส่วนที่ใช้ร่วมกัน"** เท่ากับสร้าง `sync_run.py` ขึ้นมาแล้ว แค่ยังปนอยู่ในไฟล์ที่ชื่อ `sync.py`

เหลือทางเลือกจริง ๆ แค่ 2 ทาง

```
copy-paste        แก้บั๊กต้องแก้ 2 ที่ ลืมที่ใดที่หนึ่งเมื่อไหร่ คนละพฤติกรรมทันที
แยกเป็นไฟล์กลาง    ทั้งสองทางเข้าเรียกตัวเดียวกัน แก้ที่เดียว
```

### ที่ทำ

```
                terminal              cron-job.org
                   │                       │
              sync.py                 api/cron.py
         argv → print            query param → log → HTTP
                   └───────────┬───────────┘
                         sync_run.py
                       runSteps()  ตัวงานจริง
```

```python
def runSteps(names: list[str]) -> list[dict]:
    """ไม่อ่าน argv ไม่ print ไม่รู้จัก HTTP
    คนเรียกเอาผลไปแสดงเองว่าจะ print ลง terminal หรือเขียน log"""
```

รับ list ของชื่อขั้นตอน คืนผลของแต่ละขั้น จบ

| ไฟล์ | รับงานเข้ายังไง | ส่งผลออกยังไง |
|---|---|---|
| `sync.py` | `argv` | `print` + exit code |
| `api/cron.py` | query param | `log.warning` + HTTP status |
| `sync_run.py` | `list[str]` | `list[dict]` |

### ได้อะไรกลับมา

- **แก้บั๊กที่เดียว** ไม่ต้องตามไปแก้ทุกทางเข้า
- **ทดสอบ `runSteps` ได้โดยไม่ต้องเปิดเซิร์ฟเวอร์** เรียกจากสคริปต์ธรรมดาได้เลย
- **เพิ่มทางเข้าที่ 3 ได้โดยไม่ต้องแตะของเดิม** เช่นปุ่มในหน้าแอดมิน

> หลักเดียวกันนี้ใช้ซ้ำอีกที่ในระบบแจ้งเตือน — `find.py` หาว่าใครควรได้รับ · `push.py` ส่ง · `syncNotify` เอามาต่อกัน **ตัวงานจริงไม่รู้ว่าใครเรียกมัน** จึงทดสอบแยกชั้นได้

## 3. ทำไมเซิร์ฟเวอร์ต้องมีคนข้างนอกมาปลุก

### 3.1 ทำไมต้องมีคนปลุก

web server **ไม่มีนาฬิกาของตัวเอง** มันรออย่างเดียว ต้องมีคนยิง request เข้ามาถึงจะขยับ
ต่อให้ไม่หลับเลยตลอด 24 ชั่วโมง ก็ไม่มีอะไรไปสั่งให้ `sync` ทำงานอยู่ดี

**จึงต้องมีคนข้างนอกที่มีนาฬิกาคอยสั่ง**

### 3.2 ทำไมไม่ตั้งเวลาในแอปเอง

1. ถ้าตั้งเวลาในโปรเซสเดียวกับ FastAPI พอ Render หลับ scheduler ตายไปด้วย
2. **คนถือนาฬิกาจึงต้องอยู่คนละเครื่องกับคนทำงาน**

### 3.3 ทำไมต้องมี cron ตัวที่ 1 ที่ไม่ได้ sync อะไรเลย

- cron ตั้ง timeout ได้สูงสุด **30 วินาที** แต่ Render ตื่นใช้เวลามากกว่านั้น (33-50 วินาที)
- ปล่อยให้หลับแล้วปลุกไม่ไหว จึงต้องยิงเรื่อย ๆ ก่อนตัวนับจะครบ 15 นาที เลยตั้งไว้ที่ **5 นาที**

## 4. การยืนยันตัวตนทำงานยังไง

ระบบมี **token 2 ตัว** คนละเรื่องกัน

### 4.1 token user — ยืนยันว่า "คนไหน"

มาจาก Supabase Auth ออกให้ตอน **login** ต้อง setup ทั้งฝั่ง Flutter (dio) และ backend

**ฝั่ง Flutter** `dio_config.dart`

```dart
final token = Supabase.instance.client.auth.currentSession?.accessToken;
options.headers["Authorization"] = "Bearer $token";
```

**ฝั่ง backend** `auth.py`

```python
authorization: str | None = Header(None)       # อ่านจาก header
token = authorization.removeprefix("Bearer ")  # ตัดคำว่า Bearer ทิ้ง
httpx.get(f"{settings.supabase_url}/auth/v1/user", ...)  # ถาม Supabase ว่าใครกันแน่
```

#### ใครตรวจ

- **Flutter** แนบ token ให้แล้วทุก request
- **backend** `authorization` เป็นข้อความยาว ๆ แต่เราต้องการแค่ token เพียว ๆ จึงตัดคำว่า `Bearer ` ออก
  → เอาไปถาม Supabase ต่อ → ถ้าตอบกลับมา OK จึงหาแถวใน `profiles`
  (เจอตัวเดิมใช้ต่อ ยังไม่มีก็สร้างใหม่)

#### ทำไม `Depends(getCurrentUser)` ต้องมี `Depends`

ความต่างของการมีกับไม่มี

```python
/a (ไม่มี Depends) -> {'server คิดว่าเป็น': 'เพื่อน'}   ← ปลอมตัวสำเร็จ
/b (มี Depends)    -> {'server คิดว่าเป็น': 'คุณ'}      ← ปลอมไม่ได้
```

| | ทำหน้าที่อะไร |
|---|---|
| `getCurrentUser()` | เอา token ไปถาม Supabase ว่ามีไหม — **เป็นยามตรวจบัตร** |
| `Depends` | บอก FastAPI ว่า **"ค่านี้ให้ไปถามยาม"** |

**ถ้าไม่มี `Depends` → `getCurrentUser` จะไม่ถูกเรียกเลย** และ `user_id` กลายเป็น query parameter ที่ใครก็พิมพ์ปลอมได้

```python
# ตัวอย่างการใช้ใน endpoint ของ user
@router.patch("/user", response_model=ProfileOut)
def updateUser(
    payload: ProfileUpdate,
    user_id=Depends(getCurrentUser),
    db: Session = Depends(get_db),
):
    ...
```

**token ยังเหมือนเดิมแม้ user คนละคนมาใช้ ถ้าเป็นเครื่องเดิม** → ไปต่อข้อ 5

## 5. แจ้งเตือนเดินทางยังไง

### 5.1 ทำไม server ส่งหามือถือตรง ๆ ไม่ได้

- server มีของพร้อมส่ง แต่ **ไม่มีท่อส่งไปที่มือถือ**
- จึงให้ server ไปคุยกับ Google แทน เพราะ Google มีท่อที่เปิดค้างกับมือถืออยู่ตลอด

> **FCM token ไม่ใช่เบอร์โทรของมือถือ แต่เป็นป้ายบอก Google ว่าท่อเส้นไหนคือเครื่องนี้**
> ไม่งั้นจะเข้าใจผิดว่าเป็นที่อยู่ที่ยิงตรงได้

### 5.2 กุญแจ 2 ดอกต่างกันยังไง

| | `google-services.json` | Service Account `.json` |
|---|---|---|
| อยู่ไหน | ในแอป | บน server |
| ลับไหม | **ไม่** ฝังใน apk อยู่แล้ว | **ลับสุด** |
| ใช้ทำอะไร | บอกว่าแอปเป็นของโปรเจกต์ Firebase ไหน → **ขอ** token | พิสูจน์ว่ามีสิทธิ์สั่งส่งในนามโปรเจกต์นั้น → **สั่งส่ง** |

**คนละทิศทาง คนละเครื่อง** — ดอกแรกใช้รับ ดอกที่สองใช้ส่ง

### 5.3 ทำไมต้องมี `match_notified`

เก็บว่าเคยส่งแจ้งเตือนของแมตช์นั้นไปแล้ว

```python
if (profile_id, match_id) in already:
    continue

# 19:00  ไม่มีในสมุด  →  ส่ง  →  จดลงสมุด
# 19:10  มีในสมุดแล้ว →  ข้าม
# 19:20  มีในสมุดแล้ว →  ข้าม
```

**ถ้าไม่จดไว้ ผู้ใช้จะได้รับใบเดิมซ้ำทุก 10 นาที** เพราะ `findDue` ถามว่า *"เหลือน้อยกว่าที่ตั้งไว้ไหม"* ซึ่งเป็นจริงทุกรอบจนกว่าแมตช์จะเริ่ม

เก็บคู่ `(profile_id, match_id)` เป็น primary key เพราะ **แต่ละคนตั้งเวลาเตือนล่วงหน้าไม่เท่ากัน แมตช์เดียวกันจึงถึงเวลาคนละตอน**

## 6. ค่าตั้งค่าอันไหนอยู่ในเครื่อง อันไหนอยู่ในฐานข้อมูล

### 6.1 ทำไมภาษาต้องอยู่ทั้งสองที่

ถ้าเก็บที่เดียว

```
เก็บแค่ในเครื่อง   server ไม่มีทางรู้          →  noti เป็นภาษา default ตลอด  ← บั๊กที่เจอ
เก็บแค่ใน DB      สลับภาษาแล้วจอต้องรอเน็ต   →  เน็ตหลุด = เปลี่ยนภาษาไม่ได้
```

- **แอป** อ่านจาก `SharedPreferences` เพื่อวาดจอ ต้องได้ทันทีไม่ต้องรอเน็ต
- **server** อ่านจาก `profiles.language` ตอนประกอบข้อความแจ้งเตือน ซึ่งเป็นตอนที่แอปอาจถูกปิดสนิท **ถามไม่ได้ จึงต้องรู้ล่วงหน้า**

### 6.2 ทำไมสวิตช์ปิดแจ้งเตือนไม่มีคอลัมน์

**ปิด = ลบแถวใน `device_token`**

```
เปิด   setupNoti()   →  POST /user/device        →  มี 1 แถว
ปิด    removeNoti()  →  DELETE /user/device/...  →  ไม่มีแถว
```

และ `findDue` มีบรรทัดนี้อยู่แล้วตั้งแต่ต้น

```python
my_tokens = tokens.get(profile_id, [])
if not my_tokens:
    continue        # ไม่มีเครื่องให้ส่ง ข้ามไป
```

**ไม่มี token = ไม่มีที่ให้ส่ง = ไม่ส่ง** จบในตัว ไม่ต้องเพิ่มคอลัมน์ ไม่ต้องเพิ่มเงื่อนไข

`findDue` ข้ามผู้ใช้ที่ไม่มีเครื่องลงทะเบียนอยู่แล้ว **ฝั่ง server จึงไม่ต้องรู้ว่ามีสวิตช์นี้อยู่เลย** — สถานะถูกแสดงด้วยการไม่มีข้อมูล แทนที่จะเป็นธงบอกสถานะ
